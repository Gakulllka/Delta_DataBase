# Delta-tasker — операционный монитор

> Не трекер задач в смысле Jira. Ядро — **месячный бюджет часов между аналитиком и руководителем**: план и факт по каждой задаче, лимит месяца на домен, автоматическое отсечение при перерасходе, двусторонние сигналы. Итог месяца — версионируемая презентация.

## Как устроен процесс

1. У **домена** есть план часов на каждый месяц: `Domain.monthlyPlans` — JSON `{"YYYY-MM": часы}`.
2. **Задача** принадлежит домену и месяцу, несёт `planH` и `factH`. Оба — строки, потому что принимают **формулы**: `2+3*4` вычисляется парсером `evalExpr` без `Function()`.
3. Задача может быть больше месяца: `totalBudgetRequested` → `budgetAllocated` → `budgetRollover`.
4. При перерасходе `computeFirstToCut` подбирает кандидатов на отсечение: низкий приоритет → не начатые → меньший бюджет. Руководитель защищает задачу флагом `excludeFromCut`.
5. **Двусторонние сигналы:** руководитель ставит `executiveFlag` (`escalate` / `pause` / `cancel` / `request_status`), аналитик отвечает `approvalStatus`.
6. В конце месяца — презентация: `generateSlides` + снимок `DomainMonthlySnapshot` с версиями.

### Номер задачи — ключ накопительного учёта

`num` **намеренно повторяется** из месяца в месяц: это одна работа, растянутая во времени. «Итого, ч» — сумма факта по всем месяцам с начала истории. Ключ — `num`, а не `id`.

> [!info] Семантика «Итого» (зафиксирована 2026-08-10)
> «Итого» = накопление по `num` (вечная задача) + факт текущей строки. `buildTotalFactMap` (`lib/metrics.ts`) итерирует всю историю из `dataByYearMonth` (прошлые годы целиком + текущий год до текущего месяца), tombstone'ы (`_deleted`) пропускаются. Та же функция используется в `lib/slides.ts` (заменила локальную `buildPrevTotalFactMap`) и прокинута через `usePresentation` → `generateSlides`. `prevMonth` в слайдах корректно переходит через границу года (у января — декабрь прошлого года). См. [[Ошибки]].

## Перенос задач

Перенос — это **копирование** незавершённых задач в новый месяц. Оригинал остаётся на месте.

| Правило | Поведение |
|---------|-----------|
| Что переносится | Всё, кроме статусов из `CLOSED_STATUSES` (Выполненная, Контроль на прод, Завершенная) |
| Повторный запуск | Задача пропускается, если в целевом месяце уже есть незакрытая строка с тем же `num` |
| План | Переносится **остатком**: `план − накопленный факт`, не меньше нуля |
| Сбрасывается | `executiveFlag`, `approvalStatus` → `approved`, `statusChangedAt`, `daysInStatus`, `budgetAllocated`, `budgetRollover`, `isFirstToCut`, `comment` |
| Сохраняется | `totalBudgetRequested` (свойство задачи, а не месяца), `excludeFromCut` (защита руководителя) |
| Результат | `{ transferred, skipped }` — диалог показывает «Перенесено: 0 · уже было в Июне: 7» |

Одиночный перенос задачи между месяцами (`moveTasks`) — настоящее перемещение с сохранением `id`.

> [!danger] Таблица выше описывает ЗАДУМАННОЕ поведение. Код работает иначе
> Сверено с реализацией 2026-08-29 (`lib/transfer.ts`, выделен из `store.ts`).
> Расхождений три, все зафиксированы тестами как есть:
>
> 1. **Другой набор статусов.** Не переносятся «Выполненная», «Завершенная»
>    и **«Отменено»**. То есть «Контроль на прод» переносится, хотя входит
>    в `CLOSED_STATUSES`, а «Отменено» не переносится, хотя в него не входит.
> 2. **Проверки на дубли нет.** Повторное нажатие «Перенести» создаёт полную
>    копию всех задач в целевом месяце. Диалог «Перенесено: 0 · уже было
>    в Июне: 7» в коде не реализован — функция возвращает одно число.
>    Дубли по `num` опасны: «Итого» считается накоплением именно по номеру.
> 3. **План переносится целиком,** а не остатком `план − накопленный факт`.
>
> Сбрасываются только `factH` и `commentLog`. Поля `executiveFlag`,
> `approvalStatus`, `budgetAllocated`, `budgetRollover`, `isFirstToCut`,
> `comment`, `statusChangedAt`, `daysInStatus` переносятся как есть.
>
> Требует решения: это дефект реализации или документация опережает код.

## Мобильный интерфейс

На телефоне таблица заменяется карточками (реализованы внутри `views/table-view.tsx`, блок `md:hidden`): девять колонок в горизонтальном скролле на 375 px нечитаемы. Переключение через `md:hidden` / `hidden md:block`.

**Карточка свёрнутая:** номер, очередь, статус, название, план/факт, прогресс.
**Раскрытая:** приоритет, итого, остаток, дни в статусе, комментарий.

Редактирование в карточку не встроено — идёт через шиты и карточку задачи.

**Bulk-операции на мобиле** (2026-08-10, Этап 6): долгое нажатие на карточку задачи (>500мс) → режим выбора (с тактильной вибрацией если доступно). В режиме выбора тап переключает чекбокс; bulk-бар (Статус/Приоритет/В беклог/Удалить/Сбросить) фиксируется снизу над нижней навигацией. Вне режима выбора тап открывает детали задачи.

**Summary-бар «Итого» на мобиле** (2026-08-10): компактная sticky-плашка (План/Факт/Итого/Прогресс) под мобильной верхней панелью — ключевая метрика продукта видна при скролле.

**Фильтры на мобиле**: чипы статусов и приоритетов в горизонтальном скролле + кнопка «Сбросить».

**Нижняя навигация:** Задачи · Беклог · Вопросы · Слайды · Протоколы · Чат.
Дашборд не добавлен сознательно — инструмент не используется. Админ-панель и «Дизайн» на мобильном пока недоступны.

**Режимы интерфейса вкладки «Задачи»** (2026-08-10, `store.uiMode`):
- **`simple` (по умолчанию)** — тулбар: Поиск + Добавить + Фильтр + «Ещё» (Перенести, Сортировка, Файлы). Настройки группировки скрыты, пустые группы скрыты по умолчанию. Минимум визуального шума.
- **`detailed`** — полный тулбар (Сортировка, Перенести, Файлы отдельными кнопками) + панель настроек группировки.

Переключатель — иконка в тулбаре (Rows3/AlignJustify), выбор персистится. Summary-бар «План/Факт/Итого/Прогресс» показывается в обоих режимах (ключевая метрика продукта).

## Роли и доступ

Модель — **«единый общий мир»**: воркспейсов нет, домены глобальны и видны всем. Двухуровневая модель прав (миграция 2026-08-10):

**1. Глобальная роль** (`User.role`, осталась только для admin-панели):
| Роль | Права |
|------|-------|
| `admin` | Всё + `/admin`-панель (блокировка/роли/смена пароля). Присваивается **первому зарегистрированному**. **= creator-equivalent всех доменов**: редактирует любой домен и управляет правами без записи в `DomainEditor`. |
| `guest` | Общий гостевой аккаунт, только просмотр. |

> `editor`/`viewer`/`member` как ГЛОБАЛЬНЫЕ права к доменам больше не действуют (хранятся для обратной совместимости). Их реальные права определяются пер-доменно.

**2. Пер-доменная роль** (`DomainEditor.role`, новая колонка):
| Роль | Права |
|------|-------|
| `creator` | Полный доступ + управление правами (выдавать/отозвать/передавать создательство) + уведомления владельца. Может быть несколько (право передаётся). |
| `editor` | Редактирование домена. |
| `viewer` | Только просмотр (запись фиксирует явный доступ). |

Все проверки на сервере (`src/lib/auth.ts`): `getDomainRole`, `canEditDomain`, `canManageDomainAccess`, `getEditableDomainIds`, `isDomainOwner`. Workflow запросов доступа — `EditRequest` (pending/approved/rejected), одобряет `creator` (+ admin).

**Миграция данных** (`prisma/migrations/20260810000000_add_domain_editor_role.sql`): `Domain.createdById` → `creator`-запись, существующие `DomainEditor` → `editor`. Запускать ПОСЛЕ `npx prisma db push`. **Требуется backup БД перед применением.**

**Создатель домена** = `DomainEditor.role='creator'` (раньше — `Domain.createdById`). Уведомления получает creator (+ admin). Создательство можно передать через диалог доступа.

## Синхронизация

- **Хранение** — нормализованные таблицы `Task` и `BacklogItem`, одна строка на задачу.
- **Конфликты** — last-write-wins по клиентской метке `_ts`. При равных метках строка пишется, только если контент отличается.
- **Удаление** — мягкое, через tombstone. Физическая чистка через 60 дней.
- **Мерж на клиенте** — построчный (`mergeRows`), плюс проход `dedupeAcrossMonths`: задача, оказавшаяся в нескольких месяцах, схлопывается в версию с наибольшим `_ts`.
- **Поля вне колонок** — в JSON-строку `Task.extra`.

| Операция | Период |
|----------|--------|
| Push после изменения | дебаунс 250 мс, только активный домен |
| Pull активного домена | 10 с |
| Полный pull | 60 с |
| Резервный push | 3 мин |
| Опрос вопросов | 8 с |
| Heartbeat | 60 с |

Статусы честные: `denied` (нет прав) отличается от `offline` (нет сети).

Вместо toast:

**Лента владельца домена** — `/api/owner-notifications`, источник `ActivityLog`. Показывает: кто, что сделал, когда, какая задача и домен, а для правок — что изменилось со старым и новым значением. Свои действия владелец не видит.

События: создание, изменение и удаление задачи и позиции беклога, вопросы и ответы, **запросы доступа к домену** (с кнопками одобрить/отклонить inline).

**Попап колокольчика** — `owner-notifications-panel.tsx`, **смонтирован в рельсе** (`app-sidebar.tsx`, 2026-08-10). Popover с лентой, пагинацией по `IntersectionObserver`, прочитанностью в `localStorage` (`tracker-notifications-seen-at`). Клик по строке задачи открывает её детали (`onOpenTask` переключает домен/год/месяц). Старый `notifications-bell.tsx` удалён 2026-08-29.

**Комментарии с автором** (2026-08-10): `CommentEntry` расёрен полем `author?` (опционально для старых записей). `currentUsername` прокинут в стор (`setCurrentUsername`, вызывается из `page.tsx` при логине). `archiveComment` пишет автора в новую запись. Серверный `/api/notifications` отдаёт реального автора вместо пустой строки. Сервер `/api/sync` хранит `commentLog` как opaque JSON — изменения структуры проходят автоматически.

## Запуск

**Порт — 3003.** Задан в одном месте: переменная `PORT` в `.env`.
Next.js не читает порт из `.env` сам, поэтому запуск идёт через

```bash
npm install        # node_modules при переносе не копируется
npm run dev        # http://localhost:3003
npm run build      # prisma generate && next build
npm run typecheck  # tsc --noEmit — обязательно перед коммитом
npm run db:push
npm test           # playwright
```

Занятые порты экосистемы: 3000 — Delta-hub, 3002 — Delta-finance,
5173 — Delta-BA. Прежний конфликт Delta-tasker с Delta-hub закрыт.

Юнит-тесты дают опору для дальнейшего разбора крупных файлов: раньше такой

## Дизайн

### Цвет — одно правило

Всё берётся из `src/lib/tokens.ts` или из переменных `--tracker-*`.
Хардкод hex в компонентах: было 344, стало **одно осознанное место**
(активный год на рельсе). Остальное — запасные значения внутри `var()`
и `presentation-theme.ts`, где значения обязаны быть литералами: слайды
выгружаются в самостоятельный HTML без доступа к переменным CSS.

> [!danger] Палитру статусов и приоритетов НЕ ТРОГАТЬ
> Она повторяет цвета Planfix и служит визуальным мостиком между Delta
> и внешней системой: человек, работающий в обеих, узнаёт статус по цвету
> не читая. Схлопывать её в четыре «фазы» ради монохрома **нельзя** —
> это потеря связи, а не наведение порядка. Именно потому, что весь
> остальной интерфейс чёрно-белый, эти цвета и читаются.
> Записано в коде `lib/tokens.ts` и в `AGENTS.md`, раздел 11.

Семантика состояния приведена к ДНК: `success` `#3F9E6E` и `warning`
`#C08A2D` вместо `#22c55e` и `#f59e0b` из палитры Tailwind — те ярче
и спорили с палитрой статусов.

### Манга — где звучит, где молчит

Приёмы (растр, линии концентрации, крупный контур, толщина вместо
прозрачности) живут **только в хроме**: заставка, вход, выбор домена,
пустые состояния, презентация.

В рабочей области их нет. На список задач смотрят по восемь часов —
там белая бумага, чернильный текст, цветной статус и ничего лишнего.

### Презентация (переписана 2026-09-01)

**Рамка:** отчёт бизнес-аналитика о своей работе для руководителя отдела,
показывается **вживую с рассказом**. Из этого следует устройство.

Слайды разреженные: когда рассказываешь сам, плотный текст на экране
конкурирует с говорящим — человек читает вместо того, чтобы слушать.
Порядок «от факта к выводу», вывод в конце: для живого показа это верно,
для читаемого файлом отчёта было бы наоборот.

| Слайд | Отвечает на вопрос |
|-------|--------------------|
| Титул | Месяц, год, домен |
| Как прошёл месяц | Задач, сделано, осталось, часы из бюджета. Полосы за три месяца — по ним видно перерасход как явление, а не как одна цифра |
| Работа | Что закрыл и что осталось. Номера — ссылки в PlanFix, у незакрытых видна степень готовности. Причины незакрытого не показываются: аналитик проговаривает их голосом |
| Что дальше | Обязательства по переходящим, свободный остаток, беклог, крупные задачи, сценарии |
| Итог месяца | Обязательные плюсы, что требует внимания, вывод |

> [!important] Порядок счёта на слайде «Что дальше»
> Сначала обязательства по незакрытым задачам (план минус **накопленный**
> итог), и только остаток бюджета можно предложить под беклог. Если считать
> наоборот, слайд покажет, что беклог влезает, хотя часы уже обещаны — это
> ложь руководителю.
>
> На данных августа 2026: обязательства 266.95 ч при полном месяце 240 ч,
> свободных часов **нет**, не хватает 26.95. Слайд говорит это прямо и
> сценариев не предлагает — выбирать не из чего. Это ответ, а не поломка.

**Крупная задача** — остаток больше 120 ч (половина полного месяца). Ищется
и в беклоге, и среди переходящих. Сценарии предлагаются только при ОДНОЙ
крупной: при двух перебор превращается в таблицу перестановок, которую на
встрече не обсудить.

**Нулевой бюджет** означает «задачи брать не планировали». Любой отработанный
час при нём — законный перерасход, и слайд называет часы, которые вычтутся
из бюджета следующего месяца.

**Оформление** следует теме приложения. Отдельного переключателя нет: слайды
делаются из интерфейса и не должны с ним расходиться.

### Выводы ИИ

**Презентация не оценивает работу аналитика.** Оценку даёт руководитель,
а отчёт приносит основания. Поэтому положительные факты — не похвала,
а трудные факты, и каждый обязан называть конкретную задачу или число.
Как только формула становится общей («хорошая динамика», «эффективная
работа»), обязательный позитив превращается в ритуал, который через два
месяца перестают читать.

Факты ищутся по убыванию силы (`lib/month-facts.ts`):

1. Закрыта задача, тянувшаяся несколько месяцев
2. Задача доведена до конца, хотя вышла за план — не бросили
3. Закрыты задачи наивысшего приоритета — сделано главное
4. Уложились в бюджет
5. Незакрытых стало меньше, чем в прошлом месяце
6. Закрыто больше, чем месяцем ранее
7. Запасной: продвинулись по N задачам, отработано M ч

Граница: месяц без единого отработанного часа возвращает **пустой список**.
Положительного факта в таком месяце не существует, и общая фраза на его
месте была бы тем самым ритуалом. Пустой раздел честнее пустых слов.

**Промпт** (`lib/ai-prompt.ts`): живой язык, полные фразы, опора на
конкретные задачи, прямой запрет на «эффективность», «оптимизацию»,
«требует вмешательства». Отдельным пунктом — требование обязательно найти,
что получилось, даже в тяжёлый месяц.

В данные модели уходят комментарии задач, накопленный итог и бюджет месяца.
Раньше уходил огрызок из пяти полей, и выводы получались общими словами
о процентах.

### Починено по дороге

1. **Мигание при загрузке.** Светлые токены не были объявлены в CSS вообще —
   выставлялись из JS после отрисовки. На `/admin` тема не применялась вовсе.
2. **Плашки статуса и приоритета** были заданы чёрным по белому — в тёмной
   теме остались бы яркими пятнами.
3. **Заставка, вход и выбор домена** описаны как «единые для всех, без
   привязки к теме», но брали цвета из токенов темы: тёмный текст ложился
   на тёмный фон. Закреплены на графит-бумагу, как рельса.
4. **Опечатки в именах токенов:** `--tracker-bg` и `--tracker-card` не
   существуют (правильно `--tracker-bg-main` и `--tracker-bg-card`).
   Работало только за счёт запасных значений в `var()`.
5. **Мёртвый посев темы** в `auth-screen`: писал в ключ
   `task-tracker-storage`, тогда как хранилище называется
   `task-tracker-store`. Запись уходила в никуда.
6. **Ключ Gemini не работал.** Диалог ввода находился внутри вкладки
   «Чат». Со слайдов он вызывался, но вкладка не смонтирована — окно
   не появлялось, оставалась только надпись «Сначала введите ключ».
   Плюс ключ жил в `useRef` и стирался при перезагрузке.
7. **«Итого» в окне задачи показывало факт месяца** вместо накопления:
   `getTaskMetrics` без карты накопления подставляет `totalH = факт`.
   У #42465 стояло 4 ч при реальных 20.25.
8. **«Загрузка» месяца считалась от суммы планов** и показывала 228 %:
   планы задач копятся за всё время их жизни и перекрывают бюджет в разы.
9. **Список закрытых статусов был продублирован строками** в
   `task-detail-dialog` и разошёлся: «Завершена» вместо «Завершенная»,
   «Отложена» вместо «Отложенной» — две строки из пяти не совпадали
   ни с чем.
10. **Цвет на слайде выводов задан строкой `"acA"`** вместо переменной —
    не цвет, браузер игнорировал. Раздел «Риски» содержал строку
    «Все задачи закрыты».
11. **Заготовка выводов без ИИ выносила приговоры** — «Низкая
    эффективность — необходимо пересмотреть процессы» — выведенные
    из двух чисел. В отчёте руководителю это читается как мнение системы.

## Известные расхождения

1. **История миграций не источник правды.** Модели в схеме, миграций мало.
   Схема накатывается через `db push`. Миграция ролевой модели
   (`prisma/migrations/20260810000000_add_domain_editor_role.sql`) —
   запускать вручную ПОСЛЕ `db push`, требует backup.
2. **`ActivityLog` не хранит `domainId`** — лента уведомлений восстанавливает
   домен через задачу, на большом журнале неэффективно.
3. **`isGlobalEditor`/`roleCanEverEdit` в `auth.ts` — deprecated-обёртки.**
   `isGlobalEditor` теперь = admin only. `roleCanEverEdit` оставлен как грубый
   фильтр (отсекает guest/viewer). При следующем рефакторинге заменить вызовы
   на `getDomainRole`/`canEditDomain`.
4. **ESLint даёт ~15 предупреждений `react-hooks/set-state-in-effect`**
   в `admin/page.tsx`, `table-view.tsx`, `use-mobile.ts` и др. Правило появилось
   в React 19 и требует поведенческих правок — вынесено в отдельную задачу.
   `tsc --noEmit` проходит чисто.
5. **Покрытие тестами частичное.** 158 юнит-тестов закрывают импорт,
   метрики, отсечение, синхронизацию, перенос, фильтры, формулы,
   очередь беклога, корзины вопросов, расчёт следующего месяца,
   положительные факты и промпт ИИ. Плюс проверка синтаксиса CSS.
   Не покрыты: `store.ts` целиком, отрисовка слайдов, экспорт.
6. **Перенос задач расходится с документацией** — три пункта, подробности
   в разделе «Перенос задач». Поведение не менялось, зафиксировано тестами.
7. **Не сделано из ТЗ:** разгрузка панели действий и ревизия диалогов (4.3, 4.4),
   читатель буфера ошибок, админка и «Дизайн» на мобильном, переработка
   структуры слайдов.
